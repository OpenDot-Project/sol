# Sol 0.0.2 release preparation

The development source version is 0.0.2, with `v0.0.2` reserved as the intended release tag.
This page is the scope and qualification record for that release preparation.
It does not announce a published tag or assert that pending CI checks have passed.
The existing Sol 0.0.1 release and its assets remain unchanged.

Native publication is currently blocked by the four advisory records documented in the
[native dependency review](../native-dependency-review.md). Passing GC/backend validation
does not clear those records. No release date is implied by this preparation.

## Scope since 0.0.1

The initial release contained the CST frontend.
Development since that release adds PSI and structural AST views, declaration/body analysis,
the supported argument/default/generic subset, verified FIR and experimental native execution.
The source specifications describe a broader language than this executable supports.
Unsupported constructs must continue to produce diagnostics rather than partial native programs.

The native backend constructs LLVM operations through the pinned 23.1.3 C++ API bridge.
LLVM printer output is available for inspection; textual LLVM is not the compile transport.
LLD.COFF and LLD.Common are embedded native library dependencies from that same SDK.
The managed compiler does not invoke an external linker to produce its native artifacts.

Native AOT and the supported library artifacts remain restricted to the implemented FIR subset.
ORC execution occurs in a separate native child host.
The compiler's CLR heap and the guest Yellow Tea heap do not share object references or GC callbacks.
SolRT links dynamically by default; `--static-solrt-lib` selects its static runtime linkage.
The native object/descriptor contract remains provisional ABI 0.

Yellow Tea now has span allocation, precise roots/descriptors, strong and weak handles,
concurrent marking/sweeping, resident span work, bounded assists and opt-in native diagnostics.
Root handshakes remain coordinated pauses and active barriers still use the heap mutex.
There is no performance guarantee or production-readiness claim for this experimental runtime.
See the [current implementation](../yellow-tea/current-implementation.md) for exact boundaries.

## Component identities

The intended Windows x86-64 artifacts have distinct names:

| Asset | Included capabilities |
|---|---|
| `sol-0.0.2-windows-x86_64.zip` | Frontend, verified FIR subset and private .NET runtime. |
| `sol-0.0.2-windows-x86_64-native.zip` | The same managed tool plus experimental native backend/runtime components. |
| Matching `.sha256` files | SHA-256 of each exact archive. |

Their component manifests enumerate files, hashes, target and declared capabilities.
The native suffix avoids publishing two different payloads under one release asset name.
The private runtime is packaged explicitly; this is neither .NET NativeAOT nor self-contained publish.
The native component does not imply a general C++ development SDK or every Windows prerequisite.
Dependency versions and notices come from the locked component inventory.

## Publication gates

1. Complete local regression, sanitizer, formatter, linter and documentation checks for the source.
2. Review the feature PR and require all mandatory and relevant Windows 2025 checks.
3. Verify open CodeQL alerts and merge normally through branch protections.
4. Verify CI results for the exact merged source SHA.
5. Create the immutable `v0.0.2` tag only on the intended qualified source.
6. Require the tag's own package and native validation workflows to finish successfully.
7. Download those verified CI packages and confirm source/run identity and archive hashes.
8. Publish the release with the exact qualified assets, then verify its public metadata and downloads.

A passing PR run is not evidence that the merge or tag run passed.
Canceled, skipped, missing or failed checks do not satisfy a gate.
Local development build outputs are not substituted for the tag's CI artifacts.
Published tags and versioned assets are not overwritten to repair a release.
No automatic follow-up monitor is part of this preparation.

## Deliberate exclusions

This release target does not claim complete source class construction, virtual/interface dispatch,
closures, generated Windows exception unwinding, full borrowing or the complete standard library.
Native carrier fixtures do not qualify generated exception handling or ORC unwind tables.
External Sol library consumption and complete module-linking behavior remain separate work.
The runtime does not implement moving collection, a nursery or concurrent stack scanning.

Signing, full provenance, a complete SPDX 3 SBOM, fresh-machine prerequisite installation and
native dependency advisory coverage must each have their own evidence before being advertised.
The release notes must report any remaining limitations plainly rather than infer them from a green build.
The [native profiling tools](../yellow-tea/native-profiling.md) provide workload/accounting evidence;
their synthetic timing results are not a claim about arbitrary Sol applications.
