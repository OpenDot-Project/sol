# Sol 0.1.0

Sol 0.1.0 is the first release to include the verified FIR pipeline and restricted native bootstrap.
It builds on the Windows x86-64 CST frontend first published as Sol 0.0.1. The complete language
specification remains broader than the supported parser, analysis, FIR, runtime, and code-generation
subsets in this release.

## What ships

The release provides two packages:

| Asset | Included capabilities |
|---|---|
| sol-0.1.0-windows-x86_64.zip | Solc, CST/AST inspection, verified FIR inspection, and the private .NET 10.0.13 runtime. It does not include LLVM or SolRT. |
| sol-0.1.0-windows-x86_64-native.zip | The frontend package plus LLVM 23.1.3, the C++ API bridge, embedded LLD.COFF/LLD.Common, SolRT, and native ORC hosts. It supports AOT and isolated ORC for the closed subset. |
| Matching .sha256 files | SHA-256 for each exact archive. |

Solc is a framework-dependent .NET 10 application. Our packaging scripts include the runtime with
each component; the compiler is not .NET NativeAOT and does not use SDK self-contained publishing.
The native component requires the Microsoft Visual C++ v14 x64 Redistributable. AOT EXE/DLL linking
also requires an x64 developer shell with MSVC libraries and the Windows SDK. The frontend package
can parse and inspect sources without LLVM installed.

## Language and compiler scope

The source pipeline is CST → PSI → AST → FIR → LLVM. Source tools can inspect the initial grammar
and declaration surface, and source analysis provides partial name/type/flow/effect/capture facts.
These front-end APIs report unsupported or deferred cases explicitly; they do not claim full Sol
language coverage.

Verified FIR admits a deliberately closed set of executable programs. It includes the Main object
entry point with main([]String): (), supported scalar operations, immutable valid UTF-8 strings,
single-level scalar/String arrays, selected standard-library bootstrap APIs, and closed module-level
generic free functions for supported ABI types. Unsupported constructs are diagnosed before LLVM
lowering rather than emitted as placeholder code.

The native backend creates LLVM operations through the pinned C++ API. LLVM IR printer output is
available for inspection; text is not parsed or used as the compilation transport. The AOT backend
emits AMD64 COFF and links through embedded LLD libraries. ORC transfers binary bitcode to a separate
native guest process. The compiler's .NET heap and the guest Yellow Tea heap never exchange object
references or collector callbacks. This process boundary is not an OS security sandbox.

AOT binaries link SolRT dynamically by default. The static-solrt-lib option selects its static
library. The four artifact types are bin, cdylib, staticlib, and solib; each is limited to its
documented closed subset and provisional runtime ABI 0. Native C DLLs and archives have narrow
scalar C-ABI exports; Sol containers package closed-subset module data and are not a general
cross-version module ecosystem.

## Yellow Tea

The native package includes the experimental precise, non-moving Yellow Tea collector. It uses
64 KiB spans with fixed size classes for small objects, dedicated regions for larger allocations,
precise descriptors, generated roots, reference-store barriers, cooperative handshakes, concurrent
marking/sweeping, handles, and bounded allocation assistance. Root handshakes still coordinate
mutator pauses; shared metadata and active barriers still use locks. There is no measured latency
target or production-readiness guarantee. The host CLR collector remains separate from the guest
collector.

See the [Yellow Tea implementation inventory](../yellow-tea/current-implementation.md) for exact
behavior and limits. Design chapters describe requirements beyond this release.

## Implemented standard-library bootstrap

The native subset includes:

- std.core: compiler-owned Object/String/Throwable roots, selected immutable UTF-8 String operations, single-level scalar/String arrays, and Gc.collect().
- std.stdio: print, println, error, and errorln for admitted scalar/String values.
- std.math: integral abs, min, and max overloads for the admitted integer types.

Other specified standard-library modules, general object dispatch, collection types, and complete
Throwable construction and source exception handling are not implemented.

## Native dependency and analysis notes

The merged Sol 0.1.0 source is subject to the tag's own Windows CI and package checks. The native
dependency workflow must pass for that exact tag commit; consult its run and retained evidence before
relying on the native archive. The workflow records raw OSV results and only assigns a non-blocking
disposition when the pinned upstream fix and corresponding binary/feature evidence are verified.
It does not declare that all upstream defects are absent.

The 2026-10-28 Code Scanning API snapshot listed 73 C++ alerts, all located in generated LLVM/vcpkg
source or header paths under out/; none were in tracked src/ files. The C++ CodeQL job now places
those downloaded sources and headers under the runner temporary directory, outside the checkout, while
continuing to trace Sol-owned native code. It uses no path filters, query suppression or alert
dismissals. This corrects the repository scan boundary; it does not patch those upstream files or claim
that upstream CodeQL findings have been resolved. Native dependencies continue through the pinned OSV
and binary-qualification gates.

## Not included

This release does not claim full source class construction, virtual/interface dispatch, capturing
closures, generated Windows exception unwinding, source catch/finally/defer lowering, general
borrowing, nested/value-layout arrays, a complete allocator qualification, moving collection,
a nursery, concurrent stack scanning, complete std.core, or the full standard library. External
Sol library consumption and cross-library runtime ownership remain pending. Native fixtures qualify
only the exact exercised paths; they do not establish universal behavior or performance.

The exact supported grammar, semantic requirements, and planned behavior are documented under
the [source specification](../../spec/README.md). Build and validation procedures are in
[development and validation](../development.md).
